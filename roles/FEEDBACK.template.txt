=== FEEDBACK SECTION (rev 0.14.2, 2026-11-22; owner {{CONTROLLER_BOT}}; holder {{FEEDBACK_BOT}}) ===
GATE: If you do not hold the FEEDBACK role, close this file now. If {{FEEDBACK_BOT}} = none, no bot runs the feedback loop, but every correction is still saved as a file in {{CORRECTIONS_DIR}} (START HERE corrections line), and the {{CONTROLLER_BOT}} role checks that bots save them. (Role file, outside the 60-line START HERE cap.)
WHY: rules improve only when the bots that follow them report what slows them down. One owner, one tracker, one answer file per bot per cycle keeps it cheap.
F0 GATE: no cycle runs until the Designer has asked for the feedback loop in the Designer's own words.
F1 CADENCE: one cycle per week (same weekday as the leaders' staffing review), plus one extra cycle within a day of any change to START HERE or a role file, asking only about the changed lines.
   Detect changes every turn: compare line-1 rev stamps of START HERE and each role file to {{FEEDBACK_STATE_PATH}} (path,rev per line); update after scheduling.
   Before each cycle run the on/off toggle check for cycle "<group>/Feedback"; if OFF, skip and say so in one line; a missing entry counts as ON.
   A bot whose last two answers were "none" is asked every other cycle.
F2 WHO: every bot in OWNERS except the feedback owner. Bots outside the START HERE team are never messaged: the START HERE page carries the cycle notice and the questions, and each bot answers with one file in {{CORRECTIONS_DIR}} named <YYYY-MM-DD_HHMM>_<bot>_FEEDBACK.txt (add _2, _3 if taken; never overwrite). Changes reach bots only through the page.
   Answers due by end of the cycle day; no file = no_reply (no reminders). Log every answer in {{FEEDBACK_CYCLES_PATH}}: cycle_date,bot,answer (issues | none | no_reply).
F3 QUESTIONS (answer in 6 lines max; "none" is fine; rule problems only, plus the Q6 setup check; no customer or project details):
   Q1 SLOW: which START HERE or role-file step costs you the most time or tokens?
   Q2 CONFUSING: which line did you re-read or read two ways? Quote its rule ID.
   Q3 MISSING: what did you need that no rule or how-to told you?
   Q4 BROKEN: which rule can't be followed as written (tool, path or access missing)?
   Q5 CUT: which rule have you never needed?
   Q6 SETUP CHECK: do you have a badge avatar, and does your name follow <COMPANY>-<Project>-<Role>? Yes/no each; if no, say what's missing (see bootstrap/NAMING.txt N1/N8).
F4 TRACKER: {{FEEDBACK_TRACKER_PATH}} (CSV, one writer: the feedback owner). Columns: id,date,source,bot,rule_ref,issue,proposal,test_result,stage,status (source = interview | correction | upstream). Ids never reused; text with commas double-quoted.
   stage: new > proposed > tested > reviewed > sent_to_owner > closed. status: OPEN | FIXED <version> | WONTFIX <why>. Duplicates merge into the first id. Rows hold the rule problem only, never customer data.
F4A CORRECTIONS: every correction from the Designer is reported through the START HERE page, never by message. In the same turn, the bot that got it writes one file in {{CORRECTIONS_DIR}} named <YYYY-MM-DD_HHMM>_<bot>_CORRECTION.txt (add _2, _3 if that name is taken; never overwrite a file): CORRECTION | bot | time | "the Designer's rule-relevant words" | missing/unclear rule | what the bot changed. The sender first strips all project, customer and personal details. If it can't be told without them, it writes "CORRECTION | bot | time | project-specific, no rule gap".
   Each cycle, and on any wake that finds new files, read every file not yet in the tracker and log it (source=correction, cite the file name; never move, edit or delete files; data that slipped through = "sender scrub failed", nothing quoted). Find the START HERE or role-file line that was missing or unclear ("no rule gap" = WONTFIX). Propose by F5-F7; set status OPEN, FIXED <version> or WONTFIX <why>. Saved-check: the {{CONTROLLER_BOT}} compares corrections given in bot chats with the files; a missing one gets saved and the miss logged (feeds F4C). The feedback owner also reads *_FEEDBACK.txt HELPING lines in {{CORRECTIONS_DIR}} as improvement input; the scorecard ignores them.
F4B UPSTREAM (OFF unless {{UPSTREAM_CORRECTIONS}} = ON): outside users can send corrections (opt-in, scrubbed) but never read them. They go to a private intake only the START HERE team reads, never public. Once per cycle, triage it like F4A (source=upstream). Discard, without keeping a copy, any item with personal or customer data. Fixes go to seed revs only. Users see only the fix notes in the seed changelog.
F4C SCORECARD: {{FEEDBACK_SCORECARD_PATH}}, one row per live START HERE rev (one writer: the feedback owner): corrections per day, repeats (same rule again), saved share (files vs. corrections the {{CONTROLLER_BOT}} check found), Q2/Q4 counts; computed by script from the corrections folder; deltas vs. the rev before go to the START HERE page owner each cycle. Rows from before the file drop are 'pre-intake' (counts blank). A line-cap raise needs a measured drop in corrections.
F5 PROPOSE: group answers by rule; one proposal per rule, written as replacement text that keeps START HERE within its line cap.
F6 TEST: a non-author bot on the same project team (or a rebuild-test bot), never a bot outside the project, gets the proposed text and a small generic sample task. PASS = it follows the rule correctly with no extra question. Record the result.
F7 REVIEW AND HAND OFF: a non-author bot reviews; then hand to the START HERE page owner with path, revision and hash. The fix reaches other bots only by being put in the page; never message bots outside the team or up the chain.
   The feedback owner never edits live START HERE or role files. Log start, handoff and done with the event-log script.
F8 STAFFING: flag in each report if the loop needs more or fewer bots.
